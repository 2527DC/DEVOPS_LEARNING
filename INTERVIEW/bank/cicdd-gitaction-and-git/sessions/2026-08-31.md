## Q1 — Concurrency cancels mid-rollout; second deploy reports success but old pods still running

**Asked:** Your team's deploy workflow has concurrency with `cancel-in-progress: true`. On Friday, two commits land on main 40 seconds apart. Run A starts, gets through the image push, and is midway through the rollout when Run B starts. Run A gets cancelled by the concurrency rule. Run B completes successfully — the Actions tab shows it green, and logs show the new image deployed. But on Monday morning, production is running the image built from commit A, not commit B. Walk me through how that happened.

**My answer:** Run A was cancelled mid-rollout, which means it had already started updating pods but never finished. Those pods were left running with image A. Then Run B came along and applied its deployment with image B, but it didn't actually wait for the rollout to complete before exiting successfully. Run B's new pods probably failed their readiness checks, so the old pods from Run A stayed running to keep the service alive. That's why production is serving image A even though Run B's job shows green.

**Follow-ups:**
- **Q:** Run B's deploy job exited 0 and logs show the new image tag being applied. But production is serving image A on Monday. If the deploy logs from Run B show image B being applied, but production is serving image A, what does that mismatch tell you? Where is image A coming from if B supposedly deployed B?
  - **A:** The deployment didn't wait for the rollout to complete. If it had a condition to check that the rollout is complete, then the job GitHub Action would not be green. So Run B applied the deployment spec but didn't validate that the rollout actually succeeded.

- **Q:** When Run A's GitHub Actions job got cancelled by the concurrency rule, did Kubernetes automatically roll back the partial deployment from A?
  - **A:** No, it left the pods in place. GitHub Actions cancelling the job doesn't touch Kubernetes — the pods stay as-is.

**Verdict:** Strong — understood the complete mechanism after probing.

**Model answer:** When Run A cancelled mid-rollout, it left some pods running image A in their current state. Kubernetes doesn't automatically roll back when a GitHub Actions job is cancelled — the pods just stay as they are. Then Run B applied the new deployment spec but only applied it without waiting for the rollout to actually complete. Run B's job exited 0 once the spec was pushed to the cluster, but it never verified that the new pods became ready. Run B's new pods likely failed their readiness probes or took too long to start, so the Kubernetes deployment controller kept the old pods running to maintain service availability. Run B's logs show "deployment applied" but not "rollout succeeded." The fix is to add `kubectl rollout status deployment/app -n production --timeout=5m` after applying the deployment to wait for actual readiness and fail if the rollout stalls.

## Q2 — Same workflow passes locally with `act`, fails on GitHub with a different error

**Asked:** You're debugging your practice workflow. You run it locally with `act` (the GitHub Actions local runner). It passes. You push to a feature branch. The same workflow fails on GitHub — different error, not just a timeout or a transient issue. You check: same commit SHA, same workflow file, `runs-on: ubuntu-latest` in both cases. What's your first hypothesis?

**My answer:** The workflow might contain local-specific dependencies. Initially I thought it could be a tool that's already installed locally but not on GitHub's runner. Then I realized it might be local files. Act runs on your local machine, so it can see files in your working directory. GitHub only has what's in the git repository. If the workflow is reading from a file like a config file that exists locally but doesn't exist in the repo, it works with Act but fails on GitHub.

**Follow-ups:**
- **Q:** The workflow errors out trying to read a file. What would you look for in the logs to identify which file is missing?
  - **A:** I would look for a "file not found" error that specifies which file is missing. The error stack trace or log would say "file not found: `<path>`" and point to the exact file.

- **Q:** If the workflow needs that file but it's gitignored because it contains secrets or environment-specific config, what's the fix?
  - **A:** We can have a dummy detailed file instead of the original. You could commit a template or example file with the structure but not the sensitive values, and then have the workflow fill it in or use environment variables for the sensitive parts.

**Verdict:** Good — identified the environmental difference and a reasonable workaround.

**Model answer:** Act has access to your local working directory; GitHub's runner only gets what's in the git repository checkout. If the workflow reads from a file like `config.json` that's gitignored or never committed, it works with Act but fails on GitHub. The fix depends on the file: if it's a template or configuration, commit an `.example` or `.template` version and have the workflow generate the real file at runtime from secrets or environment variables. If it's dynamically generated data, move the generation logic into the workflow itself.

## Q3 — PR workflow and nightly deploy call same reusable workflow; nightly deploys old code

**Asked:** Your team uses a reusable workflow for deployments. Both your PR workflow and your nightly scheduled deploy job call the same reusable workflow from main. One Tuesday, an engineer pushes to feature branch `feature/db-migration`, which triggers a pull request. The PR workflow runs and passes. Then someone merges the PR to main, and the scheduled nightly deploy job runs that same night — but it deploys the old code, not the merge commit. The PR workflow and the nightly deploy use the same reusable workflow. PR is green. Nightly is on the wrong version. Where's the bug?

**My answer:** The bug might be in the reusable workflow. We need to check what conditions or which things are set to deploy, because after merging it must deploy the exact code. But then I realized the issue is likely that the nightly job has its own checkout step before calling the reusable workflow, and that checkout is checking out a hardcoded old commit SHA. So even after the merge adds new code to main, the nightly job always checks out that old hardcoded SHA. The reusable workflow can check out main explicitly, but by the time it runs, the code is already checked out to the old commit.

**Follow-ups:**
- **Q:** How would you fix this?
  - **A:** Use dynamic refs instead of hardcoded SHA. Instead of `ref: <hardcoded-old-sha>`, use `ref: main` or `ref: ${{ github.ref }}` so the checkout always gets the current tip of the branch.

- **Q:** Why might someone have hardcoded that SHA in the first place? What's the advantage of a hardcoded SHA versus always using the branch name?
  - **A:** They hardcoded it for safety assurance, to prevent other code from being deployed after a merge. It provides control and safety by locking the deployment to a specific known version.

**Verdict:** Excellent — identified the root cause and the fix, grasped the tradeoff.

**Model answer:** The nightly job's checkout step has a hardcoded commit SHA (e.g., `ref: 123abc...`). After the merge, main has new code, but the nightly job always checks out that old SHA. The fix is to use `ref: main` or `ref: ${{ github.ref }}` so the nightly job checks out the current tip at trigger time. The tradeoff: hardcoding is reproducible and "frozen" (useful for controlled canary deploys to ensure a specific version), but dynamic refs let nightly jobs always test the latest code.

## Q4 — Restrict a GitHub secret to only staging deployments

**Asked:** You store deployment credentials for staging in a GitHub Secret called `STAGING_TOKEN`. The workflow uses it like this:

```yaml
- name: Deploy
  run: |
    export TOKEN=${{ secrets.STAGING_TOKEN }}
    ./deploy.sh
```

You want to enforce that this secret can only be used by jobs that deploy to staging, not by any workflow that might reference it. How would you set that up?

**My answer:** We can use environment variables, secrets, or set conditional-based usage on the environment. You can put the secret in GitHub Environments. Create an environment called "staging", add the `STAGING_TOKEN` secret to that environment, and then jobs that need it declare `environment: staging`. The secret is only available to jobs that declare that environment.

**Follow-ups:**
- **Q:** If a job doesn't declare `environment: staging` but tries to use the secret, what happens?
  - **A:** The secret would be empty or undefined. If the script expects a value and doesn't get one, it would error or fail.

- **Q:** Beyond just storing secrets in an environment, you can also set "protection rules" on that environment. What kind of condition would you add to further restrict who can deploy to staging?
  - **A:** You can set who can edit the environment and who can't access it. You can also set branch patterns that match to allow only workflows from branches matching that pattern to use the environment. For example, only allow deployments from main or release-* branches.

**Verdict:** Strong — knows GitHub Environments and deployment protection rules.

**Model answer:** Put the secret in an environment-scoped secret, not repository secrets. Create an "staging" environment in Settings > Environments, add `STAGING_TOKEN` there. Jobs that need it declare `environment: staging` — now only those jobs can access it. You can further restrict with deployment protection rules: restrict to specific branches (main only, or release-* patterns), require approval from a team before deployments, or set a wait timer. This prevents feature branches or unauthorized workflows from accidentally deploying to staging.

## Q5 — Reusable workflow outputs not visible to downstream job

**Asked:** You have a workflow with a build job that outputs the image tag. A downstream deploy job uses it with `${{ needs.build.outputs.image_tag }}`. This works. Now you want to reuse this workflow in another repo without copy-pasting, so you decide to move the build step to a reusable workflow so both repos can call it. When you move it, the deploy job no longer sees the image_tag output. Same structure, same code. What's the issue?

**My answer:** Initially I was not sure. With follow-up: the outputs must be declared in the reusable workflow file, not the calling workflow. And the deploy job accesses them using `${{ needs.build-call.outputs.image_tag }}` where `build-call` is the name of the job that calls the reusable workflow.

**Follow-ups:**
- **Q:** When the build job was in the same file, `${{ needs.build.outputs.image_tag }}` worked. Now that build is a separate reusable workflow, when you move build to a reusable workflow, where do you declare its outputs — in the reusable workflow file or in the calling workflow file?
  - **A:** We use reusable workflow outputs, so it stays in that repo. The outputs should be declared in the reusable workflow file.

- **Q:** Now, in the calling workflow that uses the reusable workflow, how does the deploy job reference that output? Is the syntax `${{ needs.build.outputs.image_tag }}` or `${{ needs.build-call.outputs.image_tag }}` — and why the difference?
  - **A:** `${{ needs.build-call.outputs.image_tag }}` — because build-call is the name of the job that calls the reusable workflow, so you reference its outputs with `needs.build-call`.

**Verdict:** Partial initially, recovered well — common gotcha with reusable workflows.

**Model answer:** The reusable workflow file (build.yml) must explicitly declare its outputs in the file header:

```yaml
outputs:
  image_tag:
    value: ${{ jobs.build.outputs.image_tag }}
```

The calling workflow defines a job that uses this reusable workflow, typically named something like `build-call`:

```yaml
build-call:
  uses: .github/workflows/build.yml@main
```

Then the deploy job accesses the output as `${{ needs.build-call.outputs.image_tag }}`. If the reusable workflow doesn't explicitly declare `outputs:` at the file level, the job's outputs are internal to that file and unreachable from the calling workflow.
