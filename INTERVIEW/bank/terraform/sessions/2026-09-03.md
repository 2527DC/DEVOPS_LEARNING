## Q1 — Stale state lock after a killed apply
**Asked:** State in S3 + DynamoDB locking. Engineer's `terraform apply` on prod killed mid-run when VPN dropped Friday. Monday, all plans fail with "Error acquiring the state lock", lock info shows OperationTypeApply held by raghav@laptop. What do you do, and what must you establish before touching anything?

**My answer:** Inform all engineers to halt apply operations. Run a drift check to see what changed mid-apply, or take a copy of the state file and inspect it, and check the apply logs to see where it got stuck.

**Follow-ups:**
- Q: Every plan is blocked by the lock — what do you run, in what order, to get to a state where you can see drift? -> A: don't know
- Q: Apply was creating VPC → EC2 → RDS, SIGKILLed right after EC2. What is in the S3 state object at that moment and why? -> A: It contains the VPC and EC2 with their details.

**Verdict:** Partial — good instincts (halt the team, copy state first), correct on incremental state persistence, but could not name `force-unlock`

**Model answer:** (1) Confirm the holding process is genuinely dead before breaking anything — never force-unlock a live apply. (2) `terraform force-unlock <ID>` using the ID straight from the error; it removes the DynamoDB lock item and does not touch state. (3) Use S3 bucket versioning to diff the current state object against the prior version to see how far the apply got. (4) Plan and reconcile, hunting for orphans — resources the AWS API created whose state write never landed. (5) Real finding: prod applies from a laptop over VPN; applies belong in CI on a durable runner. Terraform persists state incrementally after each resource completes, which is why a killed apply is usually survivable.

## Q2 — `count` and a deleted middle list element
**Asked:** 4 ECR repos + 4 IAM roles created with `count = length(var.apps)` over `["auth","billing","search","notify"]`. PR removes "billing"; CI plan shows 6 changes, not 2. Explain what the plan says and why.

**My answer:** No idea. Expected it to just remove the billing IAM role and repo; guessed it might also delete the related running container and security groups.

**Follow-ups:**
- Q: How does Terraform address each ECR repo in state? Give the literal address for the `search` repo. -> A: don't know
- Q: Would `for_each = toset(var.apps)` change the plan? Yes/no and why? -> A: Yes, a lot of difference — it's a list, looping through it may have messed up, but don't know what.

**Verdict:** Fail — no model of resource addressing

**Model answer:** `count` keys state by integer index: `aws_ecr_repository.app[0..3]`. Removing the middle element shifts search 2→1 and notify 3→2. Terraform compares addresses only, so `app[1]` must be renamed billing→search and `app[2]` search→notify; repo name and role name are force-new attributes, so both are REPLACED, plus `app[3]` destroyed. 3 changes × 2 resource types = 6. Two healthy production services get destroyed and recreated (ECR repos lose all their images) in order to delete a third. `for_each = toset(...)` keys by string — `app["billing"]` — so removing it yields exactly 2 destroys and touches nothing else. `for_each` is the default for anything with identity; `count` is only for N identical copies.

## Q4 — `-var-file` does not select the workspace ⚠️
**Asked:** Team uses dev/stage/prod workspaces off one codebase with `-var-file`. Engineer runs `terraform apply -var-file=dev.tfvars` with the terminal left on the `prod` workspace from an earlier session. What happens, and how far does the damage go before anyone notices?

**My answer:** No damage — it's `-var-file=dev.tfvars`, which says the dev stage, so prod is not affected.

**Follow-ups:**
- Q: Which state object in S3 does that command read and write, and what determines that path? -> A: The dev state file in the S3 bucket gets affected, that's it.
- Q: Does `-var-file` affect state selection at all? What command would have pointed Terraform at dev state? -> A: It passes values for the variables; don't know the command.

**Verdict:** Fail — inverted mental model with production-destroying consequences. Most serious finding of the round.

**Model answer:** `-var-file` supplies variable VALUES and has zero influence on state selection. The workspace determines state, set via `terraform workspace select dev`; with the S3 backend, non-default workspaces live at `env:/<workspace>/<key>`. So the command reads PROD state, diffs it against DEV values, and applies — prod gets dev instance types, counts, CIDRs and AMIs; resources scaled down, replaced or destroyed, at full blast radius before anyone notices. This is the standard argument against workspaces for environments: one backend, one credential set, one blast radius. HashiCorp positions workspaces for short-lived parallel state (a feature branch), not environment isolation. Production teams use separate root modules and backends per environment, ideally in separate AWS accounts, with applies only from CI where the pipeline sets the workspace.

## Q5 — Secrets in state and saved plan files
**Asked:** Audit finds the prod RDS master password in cleartext in S3 state AND in the `-out=tfplan` artifact CI keeps for 30 days. The variable is already `sensitive = true`. Why didn't that help, and how do you fix it?

**My answer:** don't know

**Follow-ups:** none — moved to debrief

**Verdict:** Fail

**Model answer:** `sensitive = true` is a display feature only — it redacts CLI and plan rendering and encrypts nothing. State is plain JSON with every attribute in full; anyone with `s3:GetObject` on the bucket has the password. A saved plan is a serialized copy of the proposed state — `terraform show -json tfplan` prints it in cleartext, and it is replicated into the CI vendor's artifact store. Fix: (1) remove the secret from Terraform entirely — `manage_master_user_password = true` on `aws_db_instance` so RDS generates it, stores it in Secrets Manager and rotates it, and Terraform never sees the value; (2) rotate the exposed password, treat it as compromised; (3) harden state regardless — SSE-KMS with a dedicated key, versioning, block public access, tight IAM, since the KMS key policy is the real access control; (4) stop persisting plan artifacts, or treat them as secrets with short retention.
